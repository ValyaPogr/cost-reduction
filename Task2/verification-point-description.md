# 1\. Контекст: зачем нужна точка верификации

В процессе онбординга нового магазина ключевая проблема — **сопоставление номенклатуры** (SKU Matching) купленной сети с эталонной базой VitaStore. В AS-IS этот процесс полностью ручной:

- Товаровед в HQ открывает Excel-файл и вручную ищет соответствия через VLOOKUP.
- **80% ассортимента** просматривается вручную (Артефакт-4).
- **15% ошибок** из-за человеческого фактора: не бьются штрихкоды, слетают цены.
- Срок онбординга — **2–3 недели**.

Полная автоматизация маппинга **невозможна и опасна**:

- Fuzzy matching даёт ложные срабатывания (Артефакт-4).
- Ошибка в маппинге = продажа дорогого товара по цене дешёвого (убыток).
- Бизнес-критичные категории (лекарства, дорогая косметика) требуют повышенного контроля.

**Решение:** гибридный подход — **human-in-the-loop**. ИИ автоматизирует high-confidence позиции, человек верифицирует только low-confidence.

# 2\. Точка верификации в процессе

## Место в TO-BE процессе

```
[Выгрузка номенклатуры] → [Preprocessing в iPaaS] → [AI Service: маппинг]
                                                              │
                                          ┌───────────────────┴───────────────────┐
                                          │                                       │
                                    ≥ 95% │                                 < 95% │
                                          ▼                                       ▼
                                  [Авто-маппинг]                    [ОЧЕРЕДЬ ВЕРИФИКАЦИИ]
                                  [staging area]                                  │
                                          │                                       ▼
                                          │                          ┌──────────────────────────────┐
                                          │                          │  ТОВАРОВЕД (HQ)              │
                                          │                          │  Web-интерфейс               │
                                          │                          │  Проверка low-confidence     │
                                          │                          │  Подтверждение / исправление │
                                          │                          └────────────┬─────────────────┘
                                          │                                       │
                                          └───────────────┬───────────────────────┘
                                                          ▼
                                              [iPaaS: консолидация + валидация]
                                                          │
                                                          ▼
                                                    [SAP ERP]
                                                          │
                                                          ▼
                                                    [Cloud POS]
```

## Триггер точки верификации

Точка верификации активируется **автоматически** после этапа AI-маппинга, когда:

1. AI Service присвоил паре **confidence score \< 95%**.
2. Позиция не найдена в эталонной базе (confidence = 0%).
3. Обнаружен **конфликт**: одна позиция из старой базы соответствует нескольким ID VitaStore.
4. Категория товара помечена как **критичная** (лекарства, детское питание, дорогая косметика) — порог может быть повышен до 98%.

**Важно:** если все позиции имеют confidence ≥ 95%, точка верификации **пропускается**. Процесс идёт дальше автоматически.

# 3\. Как работает confidence score

## Расчёт уверенности

AI Service присваивает каждой паре «старый SKU → VitaStore ID» оценку от 0 до 100%. Оценка формируется на основе:


|Фактор|Вес|Описание|
|:---|:---|:---|
|**Векторное сходство (embeddings)**|40%|Косинусное расстояние между названиями|
|**Fuzzy matching (Levenshtein)**|25%|Посимвольное сравнение строк|
|**Совпадение штрихкода**|20%|Точное совпадение EAN-13 / EAN-8|
|**Совпадение категории**|10%|Классификатор категорий|
|**Исторические данные**|5%|Предыдущие подтверждения товароведа|

## Пороговые значения


|Confidence|Действие|Доля от объёма (целевая)|
|:---|:---|:---|
|**≥ 95%**|Авто-маппинг без участия человека|\~80%|
|**70–94%**|Верификация товароведом (топ-3 кандидата от ИИ)|\~15%|
|**\< 70%**|Верификация товароведом \+ ручной поиск|\~4%|
|**0%** (не найдено)|Создание новой карточки или эскалация|\~1%|

**Целевая доля ручной верификации:** ≤ 20% от общего объёма (вместо 80% в AS-IS).

# 4\. Участие человека: роль товароведа

## Что видит товаровед

Товаровед работает в **web-интерфейсе верификации** (self-service, не Excel). Для каждой low-confidence позиции отображается:

1. **Исходное название** из старой базы (например, «Шамп. Head&Shoulders 400»).
2. **Топ-3 кандидата** от ИИ с указанием confidence для каждого:
   - Кандидат 1: «Шампунь Head&Shoulders 400 мл Основной уход» — 87%
   - Кандидат 2: «Шампунь Head&Shoulders 400 мл Ментол» — 72%
   - Кандидат 3: «Шампунь Head&Shoulders 200 мл» — 45%
3. **Штрихкод** из старой базы (если есть).
4. **История маппинга:** как эта позиция матчилась в других магазинах.
5. **Категория товара** и признак критичности.

## Что делает товаровед


|Действие|Когда применяется|
|:---|:---|
|**Подтвердить кандидата**|ИИ предложил правильный вариант (клик по кандидату)|
|**Выбрать другого кандидата**|Правильный вариант есть в топ-3, но не первый|
|**Найти вручную**|Ни один кандидат не подходит — поиск по базе VitaStore|
|**Создать новую карточку**|Товара нет в эталонной базе (новинка, эксклюзив)|
|**Пометить как «не матчить»**|Позиция не должна быть в базе (мусор, дубликат)|
|**Эскалировать**|Сложный случай — передать категорийному менеджеру|

## Принципы работы товароведа

1. **Не проверяет всё.** Только low-confidence позиции (≤ 20% объёма).
2. **Не ищет с нуля.** ИИ даёт топ-3 кандидата — товаровед выбирает или корректирует.
3. **Не работает в Excel.** Web-интерфейс с подсказками, горячими клавишами, массовыми операциями.
4. **Обучает модель.** Каждое подтверждение/исправление сохраняется в feedback loop.
5. **Работает параллельно.** Не ждёт завершения всего маппинга — очередь формируется потоково.

# 5\. Механизмы снижения ошибок

## 5\.1. Preprocessing (до маппинга)


|Проблема в AS-IS|Решение в TO-BE|
|:---|:---|
|«Крем д/рук синий»|Нормализация: «Крем для рук, синий»|
|«Шамп. Head&Shoulders 400»|Унификация: «Шампунь Head&Shoulders 400 мл»|
|Разные единицы (мл, г, шт)|Приведение к единому формату|
|Дубликаты в файле|Автоматическое удаление|
|Мусорные позиции|Фильтрация по бизнес-правилам|

## 5\.2. Валидация (после маппинга)

iPaaS выполняет автоматическую валидацию перед загрузкой в SAP:

- **Обязательные поля:** штрихкод, название, категория, цена.
- **Дубликаты штрихкодов:** один штрихкод не может быть у двух товаров.
- **Конфликты ID:** одна позиция не может матчиться на два ID VitaStore.
- **Бизнес-правила:** цена не может быть ниже закупочной (защита от «крема в минус»).
- **Аномалии:** резкое отклонение цены от средней по категории.

При провале валидации — возврат на доработку с отчётом об ошибках.

## 5\.3. Критичные категории

Для отдельных категорий порог автоматизации **повышается**:


|Категория|Порог|Причина|
|:---|:---|:---|
|Лекарства|98%|Регуляторные требования, здоровье|
|Детское питание|98%|Безопасность|
|Дорогая косметика (\> 3000 ₽)|98%|Финансовые риски|
|Бытовая химия|95%|Стандартный порог|
|Прочее|95%|Стандартный порог|

## 5\.4. Feedback loop (обучение модели)

Каждое действие товароведа логируется и используется для улучшения модели:

- **Подтверждение кандидата №1** → повышение веса признаков, которые привели к этому кандидату.
- **Выбор кандидата №2 или №3** → корректировка весов.
- **Ручной поиск** → добавление нового паттерна в обучающую выборку.
- **Создание новой карточки** → расширение эталонной базы.

**Эффект:** доля low-confidence снижается со временем (с 20% до 10–15% через 6 месяцев).

# 6\. Роли и ответственности


|Роль|Зона ответственности|Что НЕ делает|
|:---|:---|:---|
|**ИТ-инженер (магазин)**|Выгрузка номенклатуры, загрузка через портал, финальная проверка|Не матчит товары, не работает с Excel|
|**AI Service**|Автоматический маппинг high-confidence, расчёт confidence score|Не принимает финальное решение по low-confidence|
|**Товаровед (HQ)**|Верификация low-confidence, создание новых карточек, эскалация|Не проверяет high-confidence, не работает в Excel|
|**iPaaS**|Оркестрация, preprocessing, консолидация, валидация|Не принимает бизнес-решения|
|**SAP ERP**|Загрузка карточек, генерация событий|Не участвует в маппинге|
|**Категорийный менеджер**|Эскалация сложных случаев, утверждение новых карточек|Не работает с очередью верификации|

# 7\. Метрики точки верификации


|Метрика|AS-IS|TO-BE (цель)|Как измеряем|
|:---|:---|:---|:---|
|**Доля ручной верификации**|80%|≤ 20%|Логи AI Service|
|**Уровень ошибок маппинга**|15%|\< 1%|Сверка с SAP после загрузки|
|**Срок онбординга**|2–3 недели|5 дней|От выгрузки до готовности POS|
|**Время на 1 позицию (верификация)**|\~7 сек (VLOOKUP)|\~3 сек (web-UI)|Логи интерфейса|
|**Доля авто-маппинга**|0%|≥ 80%|Логи AI Service|
|**Точность авто-маппинга**|—|≥ 99%|Выборочный аудит|
|**Снижение low-confidence**|—|−5 п.п. за 6 мес.|Динамика по месяцам|

# 8\. Что НЕ входит в промежуточное состояние

На горизонте 2 месяцев **не реализуется**:

- **Полная автоматизация без человека.** Human-in-the-loop сохраняется.
- **Zero-touch provisioning.** ИТ-инженер всё ещё выезжает в магазин.
- **Real-time синхронизация всех справочников.** Только критичные (цены, номенклатура).
- **Автоматическое создание карточек.** Новые товары создаёт товаровед.
- **Мультиязычность.** Пока только русский язык.

Эти элементы — на финальное состояние (1 год).

# 10\. Резюме

**Точка верификации** — это ключевой элемент human-in-the-loop в TO-BE процессе онбординга магазина. Она обеспечивает баланс между:

- **Автоматизацией** (80%\+ позиций матчатся ИИ без человека).
- **Контролем качества** (low-confidence проверяет товаровед).
- **Снижением ошибок** (с 15% до \< 1%).
- **Сокращением срока** (с 2–3 недель до 5 дней).

**Человек не исключается из процесса** — он смещается с рутинного VLOOKUP на экспертные решения: подтверждение, исправление, создание новых карточек, эскалация. Это повышает качество данных и снижает риск финансовых потерь.
