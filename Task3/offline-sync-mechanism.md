# offline-sync-mechanism

# 1\. Offline-first: как магазин работает без интернета

Web POS на планшете построен по принципу **offline-first** (PWA с Service Worker и IndexedDB). Справочники, актуальные цены и кэш баллов лояльности синхронизируются в локальное хранилище планшета заранее — при каждом успешном подключении к Cloud Backend. Когда интернет пропадает, кассир продолжает работать: Web POS переключается в офлайн-режим, читает данные из IndexedDB и записывает каждую операцию (чек, возврат, начисление баллов) в локальную очередь. Фискальный чек печатается через HAL Agent и фискальный регистратор — это не зависит от облака. Наличные продажи работают полностью, а оплата картой — через Cloud Terminal Bridge, который также умеет буферизовать транзакции до восстановления связи.

# 2\. Очередь операций и Sync Service

Каждая офлайн-операция получает **уникальный идентификатор** (UUID) и **локальный timestamp** ещё до отправки в облако. Это критично для идемпотентности: если одна и та же операция будет отправлена дважды (например, из-за повторной попытки при нестабильной связи), Sync Service распознает дубликат по UUID и не создаст вторую запись. Операции складываются в **persistent queue** в IndexedDB и переживают перезагрузку планшета. Когда связь восстанавливается, Web POS инициирует **batch-отправку** очереди в Sync Service через API Gateway. Sync Service обрабатывает пакет последовательно, применяя операции к Managed DB, и публикует события в Event Bus для остальных сервисов (SAP, Loyalty, Promo Engine).

# 3\. Reconciliation и разрешение конфликтов

После загрузки офлайн-операций Sync Service запускает **reconciliation** — сверку локального состояния с облачным. Конфликты разрешаются по правилам:

- **Цены:** приоритет у облачной цены на момент операции, зафиксированной в чеке (чек неизменяем).
- **Баллы лояльности:** идемпотентное начисление по UUID операции; повторное начисление невозможно.
- **Остатки:** суммирование офлайн-продаж с текущим облачным остатком.
- **Промо:** если акция закончилась, пока магазин был офлайн, чек всё равно остаётся валидным (фискальный документ), но в отчётности помечается флагом «offline sale».

Если reconciliation выявляет аномалию (например, расхождение баланса баллов \> порога), операция помечается для ручного разбора товароведом или финансовым контролёром. Все действия логируются в ITSM/Monitoring для аудита. Такой подход обеспечивает **eventual consistency** без потери данных и без двойных списаний — ключевое требование для retail-системы, где простой кассы равен прямой потере выручки.

# Ключевые архитектурные решения


|Проблема AS-IS|Решение TO-BE|Компонент|
|:---|:---|:---|
|Монолитный POS с драйверами|Web POS (PWA) \+ HAL Agent|Web POS, HAL|
|Жёсткая связка с терминалами|Payment Gateway \+ Cloud Terminal Bridge|payGw, cloudTerm|
|500\+ локальных серверов|Managed DB \+ Redis Cache|cloudDb, cache|
|Ночной FTP-обмен|Event Bus (Kafka)|eventBus|
|Лояльность не работает офлайн|Offline-first \+ Sync Service|webpos, syncSvc|
|Ручной маппинг SKU|AI Matching Service|aiSvc|
|Реактивная поддержка|ITSM / Monitoring (SaaS)|itsm|
|Выезд инженера при открытии|Zero-touch provisioning|hal, engineer|
